For **Dev Containers**, you don't need to become a Docker expert first. You mainly need to understand these six concepts:

```text
Docker Fundamentals
│
├── Images
├── Containers
├── Volumes
├── Networks
├── Dockerfile
└── Docker Compose
```

I'll explain them using one project throughout: a simple **Python API + PostgreSQL + Redis** application.

---

# 1.1 Docker Fundamentals

## First: What problem is Docker solving?

Imagine you build a Python application.

Your laptop has:

```text
Python 3.12
Flask 3.x
PostgreSQL 16
Redis
```

Your colleague has:

```text
Python 3.10
Flask 2.x
PostgreSQL 14
Redis
```

Your application works on your machine but fails on theirs.

Docker's basic idea is:

> **Package the application and its required environment into a standardized unit that can run consistently.**

Conceptually:

```text
Your Application
      +
Runtime
      +
Dependencies
      +
Configuration
      ↓
   Container
```

---

# 1. Images

An **image is a template used to create containers**.

Think of an image as a **blueprint**.

For example:

```text
Python Image
│
├── Linux base
├── Python 3.12
├── pip
└── Python runtime
```

From that image, Docker can create a container.

```text
          IMAGE
            │
            │ create
            ▼
       CONTAINER
```

### Example

You can download a Python image:

```bash
docker pull python:3.12
```

Check images:

```bash
docker images
```

You might see:

```text
REPOSITORY   TAG      IMAGE ID
python       3.12     abc123
```

The important point:

> **An image is not normally running.**

It's the packaged template.

---

# 2. Containers

A **container is a running instance of an image**.

For example:

```bash
docker run python:3.12
```

Docker takes:

```text
python:3.12
```

and creates a container.

Conceptually:

```text
Python 3.12 Image
       │
       ▼
Python Container
       │
       └── Python process
```

You can see running containers:

```bash
docker ps
```

You can see all containers:

```bash
docker ps -a
```

---

## Image vs Container

This is one of the most important Docker concepts.

| Image                     | Container          |
| ------------------------- | ------------------ |
| Template                  | Running instance   |
| Usually immutable         | Has runtime state  |
| Used to create containers | Created from image |
| `docker images`           | `docker ps`        |

Think:

```text
Class
 ↓
Object
```

or:

```text
Blueprint
 ↓
Actual building
```

Similarly:

```text
Image
 ↓
Container
```

---

# 3. Why do we need Containers?

Suppose you have:

```text
FastAPI application
```

You can package the application into an image:

```text
┌─────────────────────────┐
│ FastAPI Image           │
│                         │
│ Linux                   │
│ Python 3.12             │
│ FastAPI                 │
│ Dependencies            │
│ Application             │
└─────────────────────────┘
```

Then:

```text
             FastAPI Image
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       Container Container Container
```

You could run multiple instances.

This is one reason containers are useful for Kubernetes later.

# 4. Volumes

Now we have a problem.

Containers are designed to be **replaceable**.

Suppose PostgreSQL is running inside:

```text
PostgreSQL Container
```

and you have:

```text
customer data
orders
payments
```

Then the container is deleted.

What happens to the data?

This is where **Volumes** come in.

---

## Volume = Persistent Storage

A Docker volume provides storage outside the container's writable layer.

Conceptually:

```text
              PostgreSQL Container
              ┌──────────────────┐
              │ PostgreSQL       │
              │                  │
              │ /var/lib/postgres
              └────────┬─────────┘
                       │
                       ▼
                 Docker Volume
                 ┌─────────────┐
                 │ Database    │
                 │ Data        │
                 └─────────────┘
```

The container can be deleted:

```text
PostgreSQL Container
       ❌ deleted
```

while the volume can remain:

```text
Docker Volume
       ✅ data remains
```

---

## Create a volume

```bash
docker volume create postgres-data
```

List volumes:

```bash
docker volume ls
```

You might eventually run PostgreSQL with:

```bash
docker run \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:16
```

The important part is:

```text
-v postgres-data:/var/lib/postgresql/data
```

It means:

```text
Docker Volume
     ↓
/var/lib/postgresql/data
```

inside the container.

---

# 5. Why Volumes Matter for Dev Containers

Suppose your development environment has PostgreSQL:

```text
Dev Environment
│
├── API
├── PostgreSQL
└── Redis
```

You don't want your development database to disappear every time you recreate the container.

So:

```text
PostgreSQL Container
       │
       ▼
PostgreSQL Volume
```

This becomes particularly useful when we introduce **Docker Compose**.

# 6. Networks

Now imagine we have three containers:

```text
API
PostgreSQL
Redis
```

The API needs to communicate with PostgreSQL and Redis.

How?

Docker **Networks**.

Conceptually:

```text
                 Docker Network
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        API        PostgreSQL      Redis
```

All three containers can communicate through the Docker network.

# 7. Container-to-Container Communication

Here's a very important Docker concept.

Suppose PostgreSQL is running in:

```text
postgres
```

and listening on:

```text
5432
```

The API can connect to:

```text
postgres:5432
```

rather than:

```text
localhost:5432
```

Why?

Because inside a Docker network:

```text
postgres
```

can act as the service/container hostname.

For example:

```text
API
 │
 │ PostgreSQL connection
 ▼
postgres:5432
 │
 ▼
PostgreSQL container
```

Similarly:

```text
API
 │
 ▼
redis:6379
 │
 ▼
Redis container
```

This concept becomes **very important** when we create your Dev Container + PostgreSQL + RabbitMQ + Redis environment.

---

# 8. `localhost` vs Container Name

This causes a lot of beginner confusion.

Suppose:

```text
Mac
│
├── VS Code
│
└── Docker
     │
     ├── API
     └── PostgreSQL
```

Inside the API container:

```text
localhost
```

means:

> **The API container itself.**

It does **not** mean your PostgreSQL container.

Therefore:

```text
❌ localhost:5432
```

might be wrong.

Instead:

```text
✅ postgres:5432
```

because `postgres` identifies the PostgreSQL service/container on the Docker network.

# 9. Dockerfile

Now the question becomes:

> How do I create my own Docker image?

That's what a **Dockerfile** is for.

A Dockerfile is a set of instructions for building an image.

Example:

```dockerfile
FROM python:3.12

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

Let's understand it.

---

## `FROM`

```dockerfile
FROM python:3.12
```

Start from an existing image.

So:

```text
python:3.12
```

becomes your base.

---

## `WORKDIR`

```dockerfile
WORKDIR /app
```

Set the working directory inside the image/container.

---

## `COPY`

```dockerfile
COPY requirements.txt .
```

Copy the file into the image.

Then:

```dockerfile
COPY . .
```

copies your application code.

---

## `RUN`

```dockerfile
RUN pip install -r requirements.txt
```

Run a command while building the image.

---

## `CMD`

```dockerfile
CMD ["python", "app.py"]
```

Defines the default command when the container starts.

---

# 10. Dockerfile → Image → Container

This relationship is extremely important.

```text
Dockerfile
     │
     │ docker build
     ▼
Docker Image
     │
     │ docker run
     ▼
Docker Container
```

For example:

```bash
docker build -t my-python-app .
```

Now:

```text
Dockerfile
    ↓
my-python-app:latest
```

Then:

```bash
docker run my-python-app
```

creates/runs:

```text
my-python-app container
```

# 11. Docker Compose

Now imagine your application has:

```text
FastAPI
PostgreSQL
Redis
RabbitMQ
```

Running each manually would be painful.

You'd need commands like:

```bash
docker run ...
docker run ...
docker run ...
docker run ...
```

And you'd have to configure:

* Networks
* Volumes
* Ports
* Environment variables
* Dependencies

This is where **Docker Compose** helps.

> **Docker Compose lets you define and run a multi-container application using a YAML file.**

---

# 12. Simple Compose Example

Create:

```text
docker-compose.yml
```

Example:

```yaml
services:

  api:
    build: .
    ports:
      - "8000:8000"
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: password
    volumes:
      - postgres-data:/var/lib/postgresql/data

  redis:
    image: redis:7

volumes:
  postgres-data:
```

Now you have:

```text
                  Docker Compose
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
       API         PostgreSQL        Redis
        │              │              │
        └──────────────┼──────────────┘
                       │
                  Docker Network
                       │
                       ▼
                 postgres-data
                    Volume
```

---

# 13. What Does Compose Give You?

Instead of manually creating everything:

```text
API container
PostgreSQL container
Redis container
Network
Volume
```

you describe the desired architecture:

```yaml
services:
  api:
  postgres:
  redis:
```

Then:

```bash
docker compose up
```

Compose creates/starts the required resources.

You can stop them:

```bash
docker compose down
```

And start them again:

```bash
docker compose up
```

---

# 14. A Very Important Distinction

Docker Compose is **not** the same as Docker.

Think:

```text
Docker
│
├── Images
├── Containers
├── Volumes
└── Networks
```

Compose is an orchestration/configuration tool that helps you manage several Docker resources together:

```text
Docker Compose
      │
      ├── Container
      ├── Container
      ├── Network
      └── Volume
```

For local development, this is extremely useful.

# 15. How All Six Concepts Connect

Now let's connect everything.

Suppose we want:

```text
FastAPI
PostgreSQL
Redis
```

### Dockerfile

Defines how to build the API image:

```text
Dockerfile
     ↓
API Image
```

### Image

Template:

```text
API Image
```

### Container

Running API:

```text
API Image
     ↓
API Container
```

### Network

Allows:

```text
API Container
     │
     ├──── postgres:5432 ────→ PostgreSQL
     │
     └──── redis:6379 ───────→ Redis
```

### Volume

Keeps PostgreSQL data:

```text
PostgreSQL
     │
     ▼
postgres-data
```

### Compose

Defines everything together:

```text
docker-compose.yml
        │
        ├── API
        ├── PostgreSQL
        ├── Redis
        ├── Network
        └── Volume
```

# 18. The Six Concepts — One-Line Definitions

| Concept            | Simple meaning                                   |
| ------------------ | ------------------------------------------------ |
| **Image**          | Blueprint/template for a container               |
| **Container**      | Running instance of an image                     |
| **Volume**         | Persistent storage for container data            |
| **Network**        | Allows containers to communicate                 |
| **Dockerfile**     | Instructions for building an image               |
| **Docker Compose** | Defines and manages multiple containers/services |

If you remember only this:

```text
Dockerfile
    ↓
  Image
    ↓
Container
    │
    ├── Network → communication
    │
    └── Volume  → persistent data

Docker Compose → manages all of the above together
```

you have enough Docker knowledge to move into **Dev Containers**.
