This is the **most important practical concept** before we start writing `devcontainer.json`.

The **Dev Container Lifecycle** means:

> **What exactly happens from the moment you open a repository until VS Code is ready for you to code inside the container.**

We'll use one simple project throughout.

---

# 0.4 Dev Container Lifecycle

The complete flow is:

```text
Open Repository
      ↓
Read devcontainer.json
      ↓
Build Image
      ↓
Create Container
      ↓
Mount Source Code
      ↓
Install Tools / Extensions
      ↓
VS Code attaches
      ↓
Start Development
```

Let's understand every step.

---

# 1. Open Repository

Suppose you have a GitHub repository:

```text
my-python-app/
├── app/
│   └── main.py
├── requirements.txt
└── .devcontainer/
    └── devcontainer.json
```

You clone it:

```bash
git clone https://github.com/example/my-python-app.git
```

Then open it in VS Code:

```text
VS Code
   │
   ▼
my-python-app/
```

At this point, you're still working normally on your Mac.

```text
Mac
│
├── VS Code
│
└── my-python-app
```

Nothing has been containerized yet.

---

# 2. Read `devcontainer.json`

VS Code sees:

```text
.devcontainer/devcontainer.json
```

For example:

```json
{
  "name": "Python Development",
  "image": "mcr.microsoft.com/devcontainers/python:3.12"
}
```

This file tells the Dev Containers system:

> "I want a development environment based on Python 3.12."

Think of `devcontainer.json` as the **blueprint/configuration for your development environment**.

It can specify things like:

```text
Which image?
Which Dockerfile?
Which tools?
Which VS Code extensions?
Which ports?
Which environment variables?
Which commands?
Which user?
```

---

# 3. Build Image

This step needs an important clarification:

> **An image is not the same thing as a container.**

Think of:

```text
Image
  ↓
Template

Container
  ↓
Running instance of that template
```

For example:

```text
Python 3.12 Dev Image
        │
        │ docker run
        ▼
Python Development Container
```

### If you're using a prebuilt image

For example:

```json
{
  "image": "mcr.microsoft.com/devcontainers/python:3.12"
}
```

Docker may simply **pull the image** if it doesn't already exist locally.

```text
Docker
  │
  ▼
Does image exist?
  │
  ├── Yes → Use it
  │
  └── No → Pull it
```

### If you're using a Dockerfile

You might have:

```text
.devcontainer/
├── devcontainer.json
└── Dockerfile
```

Docker will build the image:

```text
Dockerfile
    ↓
docker build
    ↓
Dev Container Image
```

For example:

```dockerfile
FROM mcr.microsoft.com/devcontainers/python:3.12

RUN pip install flask pytest
```

The result is an image containing:

```text
Python 3.12
Flask
pytest
```

---

# 4. Create Container

Now Docker takes the image and creates an actual container.

Think:

```text
IMAGE
  │
  │ create
  ▼
CONTAINER
```

For example:

```text
┌───────────────────────────┐
│ Python Dev Image          │
│                           │
│ Python 3.12               │
│ Flask                     │
│ pytest                    │
└─────────────┬─────────────┘
              │
              ▼
       ┌───────────────┐
       │ Dev Container │
       └───────────────┘
```

The container is now a running isolated environment.

You can see it with:

```bash
docker ps
```

You might see:

```text
CONTAINER ID   IMAGE                 STATUS
abc123         python-dev            Up 2 minutes
```

---

# 5. Mount Source Code

Now comes a very important part.

Your source code is on your Mac:

```text
Mac
│
└── my-python-app/
    ├── app/
    ├── tests/
    └── requirements.txt
```

But your development tools are inside the container.

So VS Code needs to make the source code available **inside the container**.

Conceptually:

```text
Mac
│
└── my-python-app/
          │
          │ mount
          ▼
┌──────────────────────────────┐
│ Dev Container                │
│                              │
│ /workspaces/my-python-app    │
│                              │
│ app/                         │
│ tests/                       │
│ requirements.txt             │
└──────────────────────────────┘
```

This is usually done using a **bind mount**.

The important thing to understand is:

> Your source code doesn't necessarily need to be copied into the image.

Instead, it can be **mounted into the running container**.

That's why you can edit:

```text
app/main.py
```

in VS Code and immediately run it inside the container.

---

# 6. Install Tools / Extensions

Now the development environment gets configured.

For example, your `devcontainer.json` might contain:

```json
{
  "name": "Python Development",

  "image": "mcr.microsoft.com/devcontainers/python:3.12",

  "customizations": {
    "vscode": {
      "extensions": [
        "ms-python.python",
        "ms-python.vscode-pylance"
      ]
    }
  }
}
```

VS Code sees:

```text
I need:
  Python extension
  Pylance
```

and configures the development environment accordingly.

You can also configure tools such as:

```text
Python
Node.js
Terraform
kubectl
Helm
Azure CLI
Git
```

There are different mechanisms for installing these, such as:

* Dockerfile
* Dev Container Features
* lifecycle commands
* VS Code extensions

We'll learn each one separately.

---

# 7. VS Code Attaches

This is another important concept.

The container is running, but VS Code needs to **connect to it**.

Conceptually:

```text
Mac
│
└── VS Code
       │
       │ connect
       ▼
   Dev Container
       │
       ├── Python
       ├── Git
       ├── Tools
       └── Source Code
```

Once attached, VS Code becomes your interface into the container.

You'll often notice something like:

```text
Dev Container: Python Development
```

in the VS Code UI.

---

# 8. Start Development

Now you're ready.

Suppose you open the VS Code terminal and execute:

```bash
python --version
```

You get:

```text
Python 3.12.x
```

But the important point is:

> **That Python is running inside the Dev Container.**

Similarly:

```bash
pip list
```

shows the packages installed in the container.

And:

```bash
terraform version
```

would use Terraform available in the development environment.

---

# Putting Everything Together

Let's follow one complete example.

You have:

```text
my-python-app/
│
├── app/
│   └── main.py
│
├── requirements.txt
│
└── .devcontainer/
    ├── devcontainer.json
    └── Dockerfile
```

### Step 1 — Open

```text
VS Code
   ↓
my-python-app
```

### Step 2 — Read configuration

```text
.devcontainer/devcontainer.json
```

### Step 3 — Build

```text
Dockerfile
    ↓
Docker Image
```

### Step 4 — Create

```text
Docker Image
    ↓
Container
```

### Step 5 — Mount

```text
Mac source code
      ↓
/workspaces/my-python-app
```

### Step 6 — Configure

```text
Container
├── Python
├── Dependencies
├── CLI tools
└── VS Code extensions
```

### Step 7 — Attach

```text
VS Code
   │
   ▼

```

### Step 8 — Develop

```text
Write code
   ↓
Run
   ↓
Test
   ↓
Debug
```

# A Very Important Detail: Image vs Container

This is where beginners often get confused.

Imagine a **cookie cutter**.

```text
Cookie cutter
     ↓
Image
```

It defines what the cookie should look like.

Then:

```text
Cookie
     ↓
Container
```

The actual cookie is the running instance.

In Docker terminology:

```text
Docker Image
     ↓
Docker Container
```

And Dev Containers use this mechanism to create your development environment.

---

# Where Does `postCreateCommand` Fit?

You'll encounter this very soon.

For example:

```json
{
  "image": "mcr.microsoft.com/devcontainers/python:3.12",

  "postCreateCommand": "pip install -r requirements.txt"
}
```

After the container has been created, Dev Containers can execute:

```bash
pip install -r requirements.txt
```

So the lifecycle becomes:

```text
Open Repository
      ↓
Read devcontainer.json
      ↓
Get/Build Image
      ↓
Create Container
      ↓
Mount Source Code
      ↓
Configure Environment
      ↓
Run postCreateCommand
      ↓
Install VS Code Extensions
      ↓
VS Code Attaches
      ↓
Ready for Development
```

There are some nuances around the exact ordering of lifecycle hooks and extension installation, which we'll cover when we study them individually. For now, this mental model is enough.

---

# What Happens When You Reopen the Project Tomorrow?

This is another useful concept.

You close VS Code.

Tomorrow:

```text
Open VS Code
     ↓
Open project
     ↓
Dev Container already exists?
     │
     ├── Yes
     │     ↓
     │   Start/reuse it
     │
     └── No
           ↓
       Create it
```

So you don't necessarily rebuild everything every time.

Docker images and containers can be reused.

---

# What If You Delete the Container?

Suppose you delete the Dev Container:

```bash
docker rm <container>
```

Your source code can still be safe because it lives on your host/mounted workspace.

You can recreate the container from:

```text
.devcontainer/
```

That's one of the major benefits.

```text
.devcontainer/
       │
       ▼
   Blueprint
       │
       ▼
New Development Container
```

So the environment is **recreatable**.

---

# The Big Picture

This is the mental model I'd like you to remember:

```text
                    Git Repository
                          │
                          ▼
                  .devcontainer/
                          │
                          ▼
                  devcontainer.json
                          │
                          ▼
                 Dev Containers
                    Extension
                          │
                          ▼
                       Docker
                          │
                ┌─────────┴─────────┐
                │                   │
                ▼                   ▼
              Image             Existing Image
                │
                ▼
             Container
                │
        ┌───────┼────────┐
        │       │        │
        ▼       ▼        ▼
     Source   Tools   Dependencies
      Code
        │
        ▼

        │

```

### In one sentence:

> **`devcontainer.json` describes the development environment, Docker provides the container, and VS Code connects you to that container so you can develop inside a reproducible environment.**

## One terminology correction worth remembering

You'll often hear people say:

> **"Build the Dev Container."**

Technically, there are multiple things happening:

```text
Image → Build/Pull
Container → Create/Start
VS Code → Attach
```

Keeping those three concepts separate will make Docker, Dev Containers, Kubernetes, and later **GitHub Codespaces** much easier to understand.
